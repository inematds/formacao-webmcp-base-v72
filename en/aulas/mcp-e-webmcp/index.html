Lesson 4 · 15 min

MCP and WebMCP in one picture: server × page, who calls whom

The two names look like the same thing, but they are not. MCP connects an agent to a server of yours, outside the browser, and it is stable. WebMCP lets the page itself declare tools for the agent running in the browser, and it is a draft. In this lesson you separate the two in one picture and run the feature detection that keeps the site working without the API.

Start the lesson

In this lesson you will

Goal: place MCP (server) and WebMCP (page) in one picture and see feature detection with fallback running.

01 · Two paths to the same action

Click each block.

Click each block in the diagram to see what it does.

MCP: the agent goes to your server. WebMCP: the open page offers tools to the browser's agent. The HTML holds up both.

02 · Side by side

What changes between the two, in four questions.

1. Where does it run?

MCP: in a process of yours (on the agent's machine over stdio, or at an HTTP address). WebMCP: inside the open tab, in the page's JavaScript.

2. Who calls?

MCP: the client (the agent) calls the server. WebMCP: the browser's agent reads the list with getTools and runs the tool; the function that runs is the page's.

3. Is it ready?

MCP: stable, revision 2026-07-28 (tutorials with SSE and initialize are from old revisions). WebMCP: a draft that has already been renamed once (from navigator to document, accepted on 05/19/2026). Lesson 5.

SealWebMCP: experimental as of 10/19/2026 (origin trial Chrome 149–156, Edge 150).

4. What should you prepare today?

HTML that the agent reads (lesson 3) works for both. If you have a service with an API, the MCP server is the stable step. The page with WebMCP comes in as a lab, always with detection and fallback.

03 · Feature detection with fallback

The only WebMCP JavaScript in this course: check whether the API exists and, without it, leave the form as it is. Registering real tools is course 2. The detectar.mjs opens the page without the API and with an empty stub (it is not the API or the polyfill), just to show the two branches.

File · kit/site/deteccao.js
// deteccao.js — WebMCP feature detection with fallback (course 0 kit, WebMCP Program).
// Spec used: WebMCP, Community Group Draft Report from 2026-10-16 (document.modelContext).
// It is a Community Group draft, not a standard: in Chrome only with an origin trial (149–156) or a local flag.
// Without the API, nothing changes: the form above is still the path for people and agents.
(function () {
  const caminho = "modelContext" in document
    ? "WebMCP presente: aqui a página registraria as ferramentas (curso 2 da formação)"
    : "WebMCP ausente: o site segue pelo formulário, igual para todos";
  document.documentElement.dataset.webmcp = "modelContext" in document ? "sim" : "nao";
  console.log(caminho);
})();
Terminal · the two branches
cd ~/projetos/formacao-webmcp-base-v72/kit
node detectar.mjs depois; echo "saída: $?"

In both branches the "Agendar" button is still there: the fallback doesn't depend on the API. With the API present, the page would register the tools; without it, the page works the same for everyone.

Running the same test on antes.html: the page does no detection at all and has no named button. WebMCP code without "modelContext" in document breaks in a browser that doesn't have the API, which today is almost every browser.
